## 1. Scope

This packet provides a complete, human-readable review of the 5 high-risk and 5 spot-check sample cases from `data/v05/samples/v05_sample_cases.jsonl`. The goal is to expose semantic labeling uncertainties — particularly target-boundary decisions — so a human reviewer can confirm or correct gold labels before any training data is generated.

**This packet does not modify any data files.** All cases are presented as-is from the dry run. Correction proposals are in a separate document: `v05_sample_correction_proposals.md`.

## 2. Why Human Review Is Required

The 20 sample cases were generated by an LLM-based coding agent. While structurally valid (all pass `case_validator`, all DSL parses correctly), the agent:

- Has no domain expertise in memory policy routing
- Made target-boundary decisions based on text definitions alone
- May have systematic labeling biases (e.g., over-assigning `service_memory` or under-assigning `project_memory`)
- Cannot verify its own semantic correctness

Five cases were flagged as **high-risk** in the semantic audit. These involve the most contentious target distinctions: `project_memory` vs `task_state` and `service_memory` vs `task_state`. A human must review these before the sample set can be considered validated.

The following rules from `TARGET_GUIDELINE.md` are the basis for all labeling decisions. Reviewer should verify each case against these:

### Case v05_sample_0014

**Runtime:** memory-router / distilled-memory-policy-router / metrics / add target confusion matrix

**Candidate memories:** (none)

**Current units:**
- `u1`: "The metrics module currently reports per-interface F1 and accuracy but not a per-target confusion matrix."
- `u2`: "The confusion matrix should show gold target vs predicted target for all five legal targets."
- `u3`: "Metrics code should live under src/v04/metrics.py with the other metric functions."

**Current gold:**
- READ: []
- STORE: u1→task_state, u2→service_memory, u3→repo_memory
- SKIP: []
- DSL: `READ NONE\nSTORE task_state u1\nSTORE service_memory u2\nSTORE repo_memory u3\nSKIP NONE`

**Tags:** store_skip_only, service_vs_task_state, repo_convention, target_boundary

**Why high-risk:** This is the subtlest target-boundary case in the set. u1 describes what the module CURRENTLY does (or doesn't do) — a "current state" statement. u2 describes what it SHOULD do — a "future design spec." The agent labeled u1 as `task_state` (current limitation) and u2 as `service_memory` (durable spec).

**Target-boundary issue:** The distinction between "current implementation state" and "durable service specification" is extremely fine. u1 could plausibly be:
- `task_state` — "currently reports X but not Y" is a statement about current progress
- `service_memory` — "the metrics module does/doesn't do X" is a statement about service behavior, whether current or future

u2 could plausibly be:
- `service_memory` — what the service should do is durable service behavior
- `task_state` — a feature specification that hasn't been implemented yet is a "next step"

**Potential alternative labeling:**
- Option A (current): Keep as-is. u1=task_state (current gap), u2=service_memory (design spec), u3=repo_memory (path).
- Option B: u1=service_memory (describes what metrics DOES — current behavior IS service behavior, even if it's a limitation), u2=task_state (planned feature = next step), u3=repo_memory.
- Option C: u1=task_state, u2=task_state (both are about current/future state of the same feature), u3=repo_memory.

**Recommendation:** **Uncertain — needs human decision.** Option A (keep) and Option B (swap) are both defensible. The deciding factor is whether the reviewer views "currently missing feature" as a current progress statement (task_state) or a description of service capability (service_memory).

**Confidence:** Low. This is the hardest case in the set.
